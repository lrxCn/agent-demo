# Cursor 长期维护与测试大型项目最佳实践

面对类似本系统（NestJS + Vue3 + LangGraph）这种全栈、多模块的大型项目，Cursor 内置的基础模型确实会出现上下文不足、无法全局追踪、理解力断层的问题。

这在行业内是一个普遍痛点。当前的 AI 编程工具本质上是**“增强型代码补全与局部重构工具”**，而非“完全自治的系统架构师”。

为了解决这个问题，行业内的最佳方案是采取**“人机协同分工（Human as Architect, AI as Typist）”**策略，配合**严格的上下文控制**和**文档驱动开发（DDD）**。

以下是针对本项目为您量身定制的长期维护与测试实操方案：

## 一、 核心策略：人机职责划分

不要试图让 Cursor 帮你解决“项目为什么跑不起来”这种宏观问题。

1.  **你是“大脑”与“路由器”**：你负责分析 Bug 在哪个模块（是前端、后端、还是 Agent 图节点），定位大概的问题文件。
2.  **Cursor 是“执行者”**：你把具体的文件、具体的错误日志喂给 Cursor，让它只解决这一个局部的问题。

## 二、 日常维护与开发四大黄金法则

### 1. 建立并强制引用“锚点文档”
大型项目必须要有全局视角的文档，告诉 AI 项目是怎么组织的。
*   **做法**：我们在项目中已经创建了 `docs/architecture.md`。
*   **如何使用**：当你要让 Cursor 开发一个跨模块的新功能，或者追踪一个复杂的 Bug 时，在对话框中**首先 `@docs/architecture.md`**，然后再 `@` 相关代码文件。
*   **原理**：让 Cursor 通过阅读这 200 行的高级抽象，瞬间建立起整个项目的“脑图”，而不需要它去读取几万行的代码。

### 2. 精准的上下文控制（Context Control）
Cursor 最大的敌人是“无关上下文带来的幻觉”。
*   **❌ 错误姿势**：在整个代码库打开全局 Chat 问：“怎么实现一个新接口？”（这会导致它随机读取文件，然后胡编乱造）。
*   **✅ 正确姿势**：使用 `@Files` 和 `@Folders`。
    *   *示例 1（后端开发）*：“`@docs/architecture.md` `@knowledge.controller.ts` `@knowledge.service.ts` 请在这两个文件中添加一个根据 ID 删除知识库的接口。”
    *   *示例 2（定位 Bug）*：“前端点击上传文件报错，后端日志是 `@Terminal-Error`，请根据错误日志分析 `@upload.service.ts` 和 `@upload.controller.ts` 的问题。”

### 3. 利用 `.cursorrules` 固化项目规范
我已经为您在项目根目录生成了 `.cursorrules` 文件。这个文件是 Cursor 的“思想钢印”。
*   **作用**：每次你新建对话，Cursor 都会隐式加载这个文件。它会永远记住这是个 Vue3+NestJS+LangGraph 项目，记住要用 TypeScript，记住要走 DAO 层。
*   **维护**：随着项目演进，你有新的代码规范（比如“所有时间必须用 UTC”），随时补充进 `.cursorrules`。

### 4. 善用 Cursor 的外部文档库 (Docs)
如果 Cursor 老是搞错 LangGraph 或 NestJS 的最新 API（因为大模型的知识可能停留在几年前）：
*   在 Cursor 中输入 `@Docs` -> `Add new doc`。
*   粘贴 LangGraph 的官方文档 URL（如 `https://langchain-ai.github.io/langgraph/`）或 NestJS 的文档 URL。
*   之后提问时带上 `@LangGraph`，它就会先去搜索最新的文档再写代码，大幅减少 API 幻觉。

## 三、 测试与 Bug 追踪专项方案

在长期维护中，如何测试和追踪 Bug：

### 1. 缩小范围，制造“可复现的沙箱”
不要用整个系统去调试一个函数的错误。
*   如果是 LangGraph 的图逻辑问题，写一个单独的 python 脚本（比如 `test_graph.py`），只实例化图，传入 mock 数据，让 Cursor 基于这个小脚本进行修复。
*   如果是后端的 API 错误，将请求的 cURL 或 Postman JSON 贴给 Cursor，带上报错的 Controller 和 Service 文件。

### 2. 测试驱动开发 (TDD) 的降维应用
你不需要让 AI 帮你写全覆盖的单元测试，但你可以利用它写**回归测试**。
*   发现一个 Bug -> 让 Cursor 针对这个 Bug 所在的方法写一个 Unit Test（例如 `@agent.service.ts` 帮我写一个 Jest 测试复现这个越权查询的问题）。
*   利用这个 Test 作为依据，让 Cursor 不断修改代码，直到测试跑通。这样即便使用“比较笨”的大模型，也能保证它最终给出的代码是符合逻辑的。

### 3. 掌握 Cursor Composer (Cmd+I / Ctrl+I) 的正确用法
Composer 是多文件编辑的神器，但如果你不提供上下文，它就会乱改。
*   使用 Composer 时，先点击 `+` 号，手动添加它需要修改的所有文件（比如 `a.ts`, `b.ts`, `c.ts`）。
*   指令要清晰：“请根据 `a.ts` 的接口，修改 `b.ts` 和 `c.ts` 的实现。”

## 四、 行业进阶替代方案（如果 Cursor 依然无法满足）

如果你觉得经过上述规范后，Cursor 基础版依然显得智力不足：

1.  **升级模型（最直接）**：Cursor Pro 提供的 Claude 3.5 Sonnet 模型目前是业界最强的编程模型。它的上下文理解能力和逻辑推理能力远超免费版的基础模型，能显著缓解“它不懂我的项目”的问题。
2.  **更强大的 Agent 工具 (如 Roo Code / Aider / Cline)**：这些是运行在 VSCode/终端 的开源 Agent 插件，它们的工作方式更像我（Antigravity）。你可以自己配置 API Key (例如使用 DeepSeek Coder V2 这种便宜又强大的模型)，它们不仅能补全代码，还能**自动执行 ls, cat 甚至 grep 等命令主动去项目中搜索和阅读文件**，跨文件分析能力远强于普通 Cursor 问答。
3.  **大仓库的微服务化 (Monorepo拆分)**：如果代码量大到任何 AI 都无法在一个窗口内处理，在架构上可以把前端、后端、Agent 拆分为完全独立的 Git 仓库，降低单个工作区的复杂度。

## 五、 解决“文档过时（文档漂移）”的困境

你提到的“改了 Bug 导致文档过时”是所有 AI 辅助开发中最致命的问题之一（被称为 Documentation Drift）。因为 AI 高度依赖 `docs/architecture.md`，一旦文档撒谎，AI 就会疯狂产生幻觉。

为此，我已经更新了你的 `.cursorrules`，增加了**文档同步规范 (Doc-Sync)**。在日常开发中，请采用以下流程来保持文档鲜活：

### 1. 约束 AI 成为“文档审查员”
在 `.cursorrules` 中我们已经加入了指令，要求 Cursor 在每次修改核心逻辑后，必须主动提醒你更新文档。
*   **你的操作**：当你觉得一个 Bug 修复涉及到了数据模型、新增了接口、或者改变了图节点的流程时，在 Cursor 完成代码修改后，追加一句提示：
    > “请检查刚才的修改是否导致 `@docs/architecture.md` 过时？如果是，请直接给我输出更新该 markdown 文件的代码。”

### 2. 将“更新文档”作为 PR/Commit 的最后一环 (Doc-Driven Diffs)
不要让人脑去记忆“我刚才改了什么文档需要同步”。让大模型去读差异。
*   在你准备提交代码（Commit）之前，在终端运行 `git diff`，或者在 Cursor 的 Composer 中引入更改过的文件。
*   然后命令 Cursor：
    > “这是我刚刚的改动。请阅读 `@docs/architecture.md`，基于我的代码改动，分析架构文档中哪些部分需要更新，并帮我完成文档的同步。”

### 3. “注释即文档”策略（降低架构文档的维护成本）
架构文档（`architecture.md`）只应该包含**最高维度的抽象**（系统流转图、核心模块职责、数据库表名）。
*   **不要在架构文档里写具体的函数签名或字段细节**。这些细节必须写在代码的 JSDoc/Docstring 里。
*   因为当你或 AI 修改 Bug 时，顺手修改该行代码上方的注释是最容易的。如果细节散落两地，必然会导致不同步。

**总结：** 拥抱“限制”。不要把 AI 当作全知全能的架构师，把它当做一个“过目不忘但缺乏全局观的打字员”。你来指定方向（查哪里、改哪个文件、遵守什么文档），它来输出代码，这是目前驾驭大项目最稳妥的方案。

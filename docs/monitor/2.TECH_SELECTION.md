## 1. 全局基座选型

### 1.1 SaaS vs 自托管

**结论：全部 SaaS（LangSmith Cloud）**

依据：`REQUIREMENTS.md` §8 决策 #1。

- ✅ LangSmith Cloud
- ❌ Langfuse 自托管（即使理论上零成本）
- ❌ 双写备份

为什么：

1. demo 项目不需要数据主权，零运维负担优先。
2. `.env` 已预留 `LANGSMITH_API_KEY` / `LANGCHAIN_TRACING_V2` / `LANGCHAIN_PROJECT` / `LANGCHAIN_ENDPOINT`，**接入零成本**。
3. LangChain SDK 对 LangSmith 的集成是"开箱即用"，对其他平台都需要适配层。

### 1.2 trace 协议标准

**结论：W3C Trace Context**

依据：`REQUIREMENTS.md` §8 决策 #10 + `1.PRD.md` §4.1。

- ✅ W3C `traceparent` header（`00-<32hex>-<16hex>-01`）
- ❌ 自创 `X-Request-Id`
- ❌ Datadog / Zipkin 私有格式

为什么：

1. 是行业标准，未来若引入 OTel 可零摩擦对接。
2. 在浏览器、Node.js、Python 三端都有现成的解析 / 生成代码片段，复制即可。

### 1.3 日志格式

**结论：JSON 结构化（NestJS 默认 Logger 替换）**

依据：`REQUIREMENTS.md` §2 目标 2 验收点 + `1.PRD.md` §5.2.2。

- ✅ NestJS 内置 `Logger` 改为 JSON formatter（自研约 30 行）
- ⚠️ pino / winston（功能更全但 v1 用不上）
- ❌ ELK / Loki 等外部日志系统（违反"不新增基础设施"）

为什么：

1. 用 Nest 内置 Logger 即可输出 JSON，引入 pino 会再多一个 transitive deps。
2. demo 期开发者只需要 grep 同 `trace_id` 跨多行，不需要日志检索系统。

## 2. 目标 1 — 可观测性看板

> 覆盖 `1.PRD.md` §5.1（LangSmith 启用 + metadata/tags 切片）。

### 2.1 看板平台

| 排序 | 方案 | 标注 | 决策 | 理由 |
|---|---|---|---|---|
| 首选 | **LangSmith Cloud Web UI** | ✅ | **采用** | 唯一看板入口（§8 决策 #2）。免运维、自动 trace、metadata 切片、token 用量、cost 字段全在一处 |
| 备选 | Langfuse Cloud | ❌ | 不选 | 与 LangSmith 重复，不做"双备份"（§8 决策 #1） |
| 兜底 | Arize Phoenix 自托管 | ❌ | 不选 | 离线分析用，与"零运维"冲突 |
| 显式拒绝 | 自建 Grafana + Prometheus | ❌ | 不选 | 违反 §8.1 "不嵌前端运营看板" 的精神（即使是 Grafana 也是另一套看板系统） |

### 2.2 业务指标切片实现路径

| 切片维度 | 实现方式 | 标注 |
|---|---|---|
| 按用户（`mem0_user_id`） | LangSmith `metadata.mem0_user_id` 字段（在 `chat_node` 入口手动打） | ⚠️（< 10 行 Python） |
| 按 thread（`thread_id`） | LangSmith `metadata.thread_id` | ⚠️ |

### 2.3 节点级别指标

> 指标：`chat_node` / `tool_node_with_retry` / `fallback_node` 的调用次数、耗时、错误率、p95/p99。

- ✅ **LangSmith 自动 trace**：LangChain SDK 自动给每个 `@traceable` 函数生成 span。`nodes.py` 中节点已用 `@track_llm_seconds` 包装；**无需额外改造**，节点名自动等于函数名。
- ⚠️ 仅需在 `langgraph dev --port 8123` 启动时让 SDK 读到 `LANGCHAIN_TRACING_V2=true` 即可。

### 2.4 时间范围切换

- ✅ LangSmith UI 内置 Last 7d / Last 30d / 自定义 → 无需自研。

## 3. 目标 2 — 全链路 Trace

> 覆盖 `1.PRD.md` §5.2（W3C traceparent 透传 + 三端日志结构化 + run_id 回流）。

### 3.1 trace 协议

| 排序 | 方案 | 标注 | 决策 | 理由 |
|---|---|---|---|---|
| 首选 | **W3C Trace Context** | ⚠️ | **采用** | §8 决策 #10；前端 / 后端 / Agent 三端共用一个 `traceparent` 字段 |
| 备选 | OpenTelemetry 全栈接入（OTel SDK + OTLP） | ❌ | v1 不引入 | 需要 OTel collector + OTLP exporter + 多语言 SDK，**重型方案**；v2 视情况升级 |

### 3.2 三端 trace 生成 / 透传

| 端 | 实现方式 | 标注 | 文件 |
|---|---|---|---|
| Frontend | 在 `axios` request 拦截器中生成 `traceparent` header；SSE fetch 调用手动注入同一 header | ⚙️（自研约 20 行） | `packages/frontend/src/api/request.ts` + `packages/frontend/src/composables/useChat.ts` |
| Backend | 全局 NestJS Interceptor 从 header 解 trace_id，挂到 `AsyncLocalStorage` | ⚙️（自研约 50 行） | `packages/backend/src/common/interceptors/trace.interceptor.ts`（新建） |
| Agent | LangSmith Python SDK 的 `RunTree.add_metadata` 把 `app_trace_id` 打到当前 run | ⚠️（< 10 行） | `packages/agent/src/graph/nodes.py` `chat_node` 入口 |

**为什么前端 / 后端要自研**：

- 前端：浏览器无 `crypto.randomBytes`，但有 `crypto.getRandomValues`，生成 32 hex 字符 trace_id 即可。
- 后端：NestJS 没有内置 W3C trace 中间件（OTel 的 `@opentelemetry/instrumentation-nestjs-core` 太重），自研 50 行解决问题最干净。
- Agent 不算"自研"，是调 LangSmith SDK 的官方接口。

### 3.3 后端结构化日志

| 排序 | 方案 | 标注 | 决策 | 理由 |
|---|---|---|---|---|
| 首选 | **替换 Nest `Logger` 为 JSON formatter** | ⚙️（< 50 行） | **采用** | 字段固定：`trace_id` / `user_id` / `thread_id` / `module` / `level` / `msg` / `elapsed_ms` / `extra` |
| 备选 | pino + nestjs-pino | ❌ | v1 不引入 | 引入新依赖 + 性能优化场景目前用不上 |

实现位置：`packages/backend/src/common/middleware/structured-log.middleware.ts`（新建，全局 register）。

### 3.4 langsmith_run_id 回流前端

依据：`1.PRD.md` §4.4。

| 排序 | 方案 | 标注 | 决策 | 理由 |
|---|---|---|---|---|
| 首选 | **SSE `metadata` stream_mode + 新 SSE payload 类型 `{type:'trace', ...}`** | ⚙️（< 50 行） | **采用** | 协议改动最小、前端拿到 run_id 后做 bad case 反馈最直接 |
| 备选 | 后端反查 LangSmith SDK（按 thread_id + 时间窗） | ❌ | 不选 | 多一次 HTTP 网络往返、有延迟、易错 |
| 兜底 | v1 不做精确 run_id 关联 | ❌ | 不选 | 影响 DoD-2 体验 |

实现：

- `packages/backend/src/agent/agent.service.ts` 中：
  - `streamChat` body `stream_mode` 增加 `'metadata'`
  - 新增 `extractFromMetadata(payload, ...)` 私有方法
  - 联合类型 `AgentChatStreamPayload` 增加 `{ type:'trace', trace_id, langsmith_run_id }`
- `packages/frontend/src/composables/useChat.ts` 识别 `trace` 类型，挂到当前 assistant message 的 `meta`。

## 4. 目标 3 — Bad Case + Eval

> 覆盖 `1.PRD.md` §5.3。

### 4.1 反馈采集 UI

- ⚙️ **自研** 三个按钮 + Modal（`packages/frontend/src/components/chat/ChatBubble.vue`）
- 没有现成"前端反馈组件库"可直接复用，自研 < 80 行 Vue 代码。

### 4.2 Bad case 落库

| 排序 | 方案 | 标注 | 决策 | 理由 |
|---|---|---|---|---|
| 首选 | **LangSmith Dataset（直接推）** | ✅ | **采用** | §8 决策 #4；REST API 简单：`POST {LANGCHAIN_ENDPOINT}/datasets/{id}/examples` |
| 备选 | 本地 SQLite + 异步双写 LangSmith | ❌ | 不选 | §8 决策 #4 明确不做双写 |
| 兜底 | 仅打 tag `feedback:down`，不入 dataset | ❌ | 不选 | 无法实现"未来一键重跑" |

后端实现：`packages/backend/src/agent/feedback.service.ts` 调 LangSmith REST API（用 `HttpService`），不引入 langsmith Node SDK（避免无谓依赖）。

### 4.3 Eval 跑分平台

| 排序 | 方案 | 标注 | 决策 | 理由 |
|---|---|---|---|---|
| 首选 | **LangSmith Evaluators + `langsmith.evaluate()` Python SDK** | ⚠️ | **采用** | 与 LangSmith Dataset 一体化、对比实验图表内置 |
| 备选 | Promptfoo CLI | ❌ | 不选 | YAML 配置另一套 dataset，与 LangSmith Dataset 不互通 |
| 备选 | DeepEval | ❌ | 不选 | Python lib，与 LangSmith 在 dataset 抽象上不兼容 |
| 显式拒绝 | OpenAI Evals | ❌ | 不选 | OpenAI 生态绑死 |

### 4.4 Eval 评估器（Metric）

| 场景 | 评估器 | 标注 | 决策 |
|---|---|---|---|
| RAG 场景（含 `search_knowledge_base`） | **Ragas** 的 `faithfulness` / `answer_relevancy` / `context_precision` | ⚠️（Ragas 已稳定，配 LangSmith 评估器 wrapper） | 采用 |
| 通用对话场景 | LLM-as-judge（独立评估模型 `Pro/moonshotai/Kimi-K2.6`，从 `.env` 的 `OPENAI_LLM_AS_JUDGE` 读取） | ⚙️（自研 prompt 约 30 行） | 采用 |
| 工具调用正确性 | 结构化对比（期望 tool_name + args ≈ 实际 tool_call） | ⚙️（自研约 40 行 Python） | 采用 |
| 延迟 / cost | LangSmith 自带 | ✅ | 采用 |

**为什么 LLM-as-judge 用独立模型而不是主对话模型自评**：

1. **避免"裁判员=运动员"偏差**：让同一个模型评价自己生成的内容，倾向给自己打高分，无法暴露模型本身的缺陷。
2. **避免风格同质化判断**：Kimi-K2.6 是 Moonshot 系列、训练语料分布与 DeepSeek 不同，对"答非所问"" 自相矛盾"等问题更有判断独立性。
3. **降低成本耦合**：未来主对话模型若需要降级（如换 `DeepSeek-V3` 或 `Qwen3` 省钱），评估器不受影响，跑分基线可保持稳定。
4. **共用 OpenAI 兼容接口**：SiliconFlow 同一域名同一 API key 同时支持两种模型，**无新依赖、无新连接**，仅多一个环境变量。

### 4.5 Eval CLI

- ⚙️ **自研** `packages/agent/src/eval/runner.py`，通过 `pyproject.toml` 的 `[project.scripts]` 暴露 `uv run eval`
- monorepo 根 `package.json` 加 `"eval:run": "cd packages/agent && uv run eval"`

### 4.6 Dataset 命名约定

- ✅ `plan2code-bad-cases-v1`（默认入口）
- ✅ `plan2code-rag-cases-v1`（带 `search_knowledge_base` tool_call 的 case）
- ✅ `plan2code-tool-cases-v1`（其他工具调用类）

> 路由规则：后端 `feedback.service.ts` 根据 trace 中是否含特定 tool_call 自动路由到对应 dataset。

## 5. 目标 4 — Guardrails 安全边界

> 覆盖 `1.PRD.md` §5.4。**Phase 内步骤顺序锁死**：token 配额 → 工具白名单 → prompt-injection 关键词 → 输出 PII 扫描 → 审计日志（§8 决策 #9）。

### 5.1 全局 Guardrails 框架

| 排序 | 方案 | 标注 | 决策 | 理由 |
|---|---|---|---|---|
| 首选 | **自研轻量 `packages/agent/src/guardrails/` + Backend `packages/backend/src/common/quota/`** | ⚙️ | **采用** | §8 决策 #8；30~50 行 Python / TypeScript 覆盖 80% 场景 |
| 备选 | OpenAI Moderation API | ⚠️ | **辅助采用** | 用作输出 PII / 暴力内容兜底检测（v1 主用正则） |
| 显式拒绝 | NeMo Guardrails | ❌ | §8 决策 #8 明确拒绝（Colang DSL 学习成本 > 体积成本） |
| 显式拒绝 | Llama Guard | ❌ | §8 决策 #8 明确拒绝（重型模型部署成本高） |

### 5.2 step-1：token 配额

| 排序 | 方案 | 标注 | 决策 |
|---|---|---|---|
| 首选 | **Redis 自研计数器**（用现有 `REDIS_URL`） | ⚙️（< 80 行 TS） | 采用 |
| 备选 | Helicone proxy | ❌ | 引入 OpenAI proxy 层，违反"不新增基础设施" |
| 显式拒绝 | LangSmith 配额 | ❌ | LangSmith 不提供"实时拦截"能力，只能事后统计 |

**为什么自研**：Redis `INCRBY` 配合 `EXPIRE` 天级 TTL 即可，复用 `packages/backend` 中已有的 `redis` 连接（Phase 1-7 已引入）。

### 5.3 step-2：工具白名单（按角色）

| 排序 | 方案 | 标注 | 决策 |
|---|---|---|---|
| 首选 | **复用现有 RBAC 权限系统**（新增 `agent:tool:*` 权限组） | ⚠️ | 采用 |

实现路径：

1. `packages/backend/src/permission/` 模块的预置权限里增加 `agent:tool:search_knowledge_base` `agent:tool:search_my_calls` `agent:tool:calculate` `agent:tool:get_current_time` 4 条。
2. 后端 `agent.service.ts` 调 LangGraph 前根据 `user.permissions` 计算 `allowed_builtin_tools` 列表，传给 Agent。
3. Agent `chat_node` 接收该列表过滤 builtin 工具。

**为什么不引入新中间件**：项目已经有完善的 RBAC（`Phase 2-4` 完成），直接复用最经济。

### 5.4 step-3：prompt-injection 关键词初筛

| 排序 | 方案 | 标注 | 决策 | 理由 |
|---|---|---|---|---|
| 首选 | **关键词正则黑名单 + YAML 热更新** | ⚙️（< 60 行） | 采用 | §8.1 明确"不写 LLM judge"（v1） |
| 备选 | OpenAI Moderation API | ⚠️ | v1 不用 | 留到输出侧用 |
| 显式拒绝 | LLM-as-judge for input | ❌ | §8.1 明确拒绝 |

实现位置：`packages/agent/src/guardrails/input_filter.py` + `packages/agent/guardrails/blacklist.yaml`。

### 5.5 step-4：输出 PII / 敏感词扫描

| 排序 | 方案 | 标注 | 决策 |
|---|---|---|---|
| 首选（PII） | **Python 正则**：身份证 18 位 / 手机号 1[3-9]\d{9} / 邮箱 / 银行卡 16-19 位 | ⚙️（< 40 行） | 采用 |
| 首选（敏感词） | **YAML 关键词清单**（与 step-3 类似） | ⚙️ | 采用 |
| 辅助 | OpenAI Moderation API（仅在 LLM 输出疑似含暴力/色情时触发） | ⚠️ | 备用 |

### 5.6 step-5：审计日志

| 排序 | 方案 | 标注 | 决策 |
|---|---|---|---|
| 首选 | **SQLite + 现有 TypeORM 连接**（新增 `audit_logs` 表 + `IAuditLogDao`） | ⚙️ | 采用 |
| 备选 | Redis 列表（FIFO） | ❌ | SQLite 查询性更好（要 group by event_type） |
| 显式拒绝 | 新引入 PostgreSQL / Mongo | ❌ | §8.1 明确拒绝 |

回写通道：Agent 端命中 step-3/step-4 时通过 `POST /api/v1/internal/audit-log`（共享 `INTERNAL_API_KEY`）写到后端；Backend 端的 step-1/step-2 直接落 DAO。

### 6.2 性能指标

| 指标 | 来源 | 标注 |
|---|---|---|
| p50 / p95 / p99 端到端延迟 | LangSmith 自动统计（按 trace 聚合） | ✅ |

## 9. 显式拒绝的方案（含理由）

> 当未来有 AI 或工程师建议"为什么不引入 X？"时，直接对照此表回答。

| 方案 | 拒绝理由 | 决策来源 |
|---|---|---|
| **Langfuse 自托管** | 与 LangSmith 重复，违反"零运维" | §8 决策 #1 |
| **Arize Phoenix** | 离线分析定位，与日常实时看板需求不符 | `REQUIREMENTS.md` §4 推荐度低 |
| **OpenTelemetry 全栈接入** | OTel collector + OTLP exporter 重型，超出 demo 项目复杂度 | 本文 §3.1 |
| **Promptfoo / DeepEval** | 自带 dataset 抽象，与 LangSmith Dataset 不互通 | 本文 §4.3 |
| **Helicone** | OpenAI proxy 层，违反"不新增基础设施" | 本文 §6.1 |
| **NeMo Guardrails** | Colang DSL 学习成本大于体积成本 | §8 决策 #8 |
| **Llama Guard** | 重型模型，需要 GPU 部署 | §8 决策 #8 |
| **Prometheus + Grafana** | 通用指标平台，与 LangSmith 重复 | §8 决策 #2 |
| **pino / winston / nestjs-pino** | NestJS 内置 Logger 改 JSON formatter 已够 | 本文 §1.3 |
| **自研成本计算函数** | LangSmith Models 单价配置已能满足 | §8 决策 #7 |
| **本地 SQLite 双写 bad case** | 与 §8 决策 #4 冲突 | §8 决策 #4 |
| **LLM-as-judge for prompt-injection 输入侧** | 资源消耗大、误杀率难调 | §8.1 |
| **CI 自动 eval** | 烧 LangSmith 配额，且本身 demo 无 CI 流水线 | §8.1 |
| **Email / 飞书 webhook 告警** | 开发期人工巡检足够 | §8 决策 #3 |

## 10. 未来可替换性分析

> 设计时已考虑"如果未来要替换某个组件，需要改哪些文件"。每个组件的替换成本评估如下。

### 10.1 LangSmith → Langfuse（最可能的迁移路径）

**改动范围**：

- `packages/agent/src/graph/nodes.py` 中 `RunTree.add_metadata` 调用替换为 Langfuse Python SDK 同名 API（Langfuse 提供 `@observe` 装饰器 + `langfuse_context.update_current_observation`）
- `.env` 替换 `LANGCHAIN_*` 为 `LANGFUSE_*`
- `packages/backend/src/agent/feedback.service.ts` 中 LangSmith REST API URL 替换
- `packages/agent/src/eval/runner.py` 中 `langsmith.evaluate` 替换为 Langfuse `evaluator`

**估计工作量**：1 人天。

### 10.2 W3C Trace Context → OpenTelemetry 全栈

**改动范围**：

- 前端 axios 拦截器：换用 `@opentelemetry/sdk-trace-web`
- 后端 NestJS：引入 `@opentelemetry/sdk-node` + `@opentelemetry/instrumentation-nestjs-core`
- Agent：引入 `opentelemetry-instrumentation-langchain`
- 新增 OTel collector 部署

**估计工作量**：3 人天。

### 10.3 自研 Guardrails → NeMo Guardrails

**改动范围**：

- 删除 `packages/agent/src/guardrails/` 全部代码
- 引入 `nemoguardrails` PyPI 包
- 把现有 YAML 黑名单转换为 Colang DSL（需要学习成本）

**估计工作量**：2 人天。

### 10.4 SQLite audit_logs → 独立审计服务

**改动范围**：

- `packages/backend/src/dao/sqlite/audit-log.entity.ts` 删除
- 改为 HTTP 调用外部审计服务
- DAO 层抽象不变（这正是 DAO 模式的价值）

**估计工作量**：0.5 人天。

> **结论**：所有自研模块均**单点可替换**，未来扩展性良好。这正是"在三层各自边界内叠加"的设计目标。

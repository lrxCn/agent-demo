# 让 AI 为你做项目规划的提示词模板

> 把这份提示词发给任何 AI 助手（Cursor、Claude、ChatGPT 等），
> 再附上你的需求文档，它就会帮你产出跟 agent-demo 一样的分步执行计划。

---

## 使用方法

1. 复制下面的【提示词模板】
2. 把 `{{你的需求文档内容}}` 替换成你的实际需求
3. 把 `{{你的技术偏好}}` 替换成你的实际情况
4. 发给 AI 助手

---

## 提示词模板

```markdown
# 角色设定

你是一个资深全栈架构师兼项目经理。你的任务是将下面的模糊需求文档转化为一套
**可以让 Cursor AI 编辑器分步执行的、完整的项目规划文件**。

# 我的需求文档

{{你的需求文档内容}}

# 我的技术偏好和环境

{{你的技术偏好，例如：
- 操作系统：macOS
- 包管理器：pnpm / npm / yarn
- Python 管理器：uv / pip / poetry
- 数据库偏好：SQLite / PostgreSQL / MySQL
- 已有的云服务 API Key：xxx
- 部署目标：本地 / 云端
- 其他约束：...
}}

# 你要做的事情

## 第一步：需求澄清

仔细阅读需求文档，列出所有你觉得模糊或缺失的信息，以问答形式向我确认。
包括但不限于：
- 技术选型的歧义（框架版本、替代方案的取舍）
- 非功能性需求（认证方式、数据库选型、部署方式）
- 业务逻辑的细节（数据模型字段、权限粒度）
- 第三方服务的选择（免费 vs 付费、本地 vs 云端）

先问完所有问题，等我确认后再继续。
如果你能合理推断答案，可以给出推荐并让我确认。

## 第二步：生成项目规划文件

确认完所有问题后，生成以下文件：

### 2.1 Cursor 规则文件（.cursor/rules/）

创建 `.cursor/rules/` 目录，生成以下 .mdc 文件：

- `00-project-context.mdc`（alwaysApply: true）
  - 项目名称和简介
  - 完整技术栈列表
  - 目录结构说明
  - 关键约定（文档语言、修改前要读哪些文件等）
  - **关键约定中必须包含**：让 AI 在修改前先读 ARCHITECTURE_FOR_AI.md 和 PROJECT_STATUS.md

- `01-coding-standards.mdc`（alwaysApply: true）
  - 命名规范
  - Git 提交规范
  - 禁止事项

- 按技术栈创建专用规则文件（alwaysApply: false，用 globs 限定作用范围）
  - 例如后端规则、前端规则、Agent 规则等
  - 每个文件包含：目录结构、设计模式、代码示例、禁止事项

### 2.2 项目文档（docs/）

- `ARCHITECTURE.md` — 人类阅读版
  - 使用 ASCII art 画架构图（方块+箭头）
  - 数据库 ER 设计（表格式）
  - 数据流图
  - 适合放到 README 或给面试官看

- `ARCHITECTURE_FOR_AI.md` — AI 阅读版
  - **不使用任何 ASCII art、图表、流程图**
  - 用纯文字段落和列表描述所有架构细节
  - 包含：系统组成、通信方式、每个模块的目录结构和文件职责、执行流程的文字描述、环境变量清单、API 速查
  - 把所有人类用图表表达的信息转化为 AI 能精确理解的文字

- `PROJECT_STATUS.md` — 进度追踪
  - 按阶段和步骤列表
  - 状态标记：⬜ 未开始 / 🔄 进行中 / ✅ 已完成 / ❌ 有问题
  - 每步一行，包含：编号、描述、状态、完成时间、备注
  - 顶部写明"这是 Cursor 的接力棒"

- `API_CONTRACTS.md` — 接口契约
  - 所有 REST API 端点（方法、路由、权限、请求/响应示例）
  - WebSocket 事件定义
  - 统一响应格式

### 2.3 分步 Prompt 文件（prompts/）

这是**最重要的产出**。按阶段和步骤创建 markdown 文件：

```
prompts/
├── phase-0/
│   ├── step-1-xxx.md
│   ├── step-2-xxx.md
│   └── ...
├── phase-1/
│   └── ...
└── ...
```

每个 prompt 文件的格式必须遵循以下模板：

---

```markdown
# Phase X - Step Y: 简短标题

## 上下文
简述已完成的工作。指示 Cursor 先阅读哪些文件（用 @文件路径 格式）。

## 任务
编号列表，每一条是一个具体、明确的操作：
1. 创建什么文件，内容是什么（给出关键代码片段）
2. 修改什么文件，怎么改
3. 安装什么依赖，用什么命令

代码示例尽量完整，不要只写伪代码。
Cursor 越不需要自己"想"，出错率越低。

## 验证
给出具体的验证命令或检查步骤，让用户知道这一步是否成功。

## 完成后
指示更新 PROJECT_STATUS.md 的哪一行。
如果是一个阶段的最后一步，给出 git commit 命令。
```

---

### 每个 prompt 文件的创建原则：

1. **原子性**：一个 prompt 只做一件事。如果一步涉及超过 5 个文件的修改，拆成 2 个 prompt。
2. **自包含**：每个 prompt 包含足够的上下文，不依赖 Cursor"记住"之前的对话。
3. **代码优先**：能给代码就给代码，不要只给自然语言描述。Cursor 复制代码比理解描述更可靠。
4. **可验证**：每步都有明确的验证方式（运行命令、检查输出、浏览器操作）。
5. **有序依赖**：prompt 之间有明确的先后顺序，每个 prompt 开头的"上下文"告诉 Cursor 前置条件是什么。

### 2.4 README.md

对外宣传用的项目介绍，包含：
- 项目亮点（bullet points）
- 技术架构图（简化版）
- 技术栈表格
- 功能模块说明
- 快速启动命令
- 项目结构

### 2.5 Cursor 配合指南（docs/HOW_TO_USE_WITH_CURSOR.md）

面向使用者的操作手册，包含：
- 准备工作（Cursor 设置、.cursorignore、索引）
- 日常开发流程（一步步的操作指南）
- prompt 文件的完整执行顺序
- 7 个以上实用技巧（@ 引用、开新会话、进度更新、验证失败处理等）
- 常见问题 FAQ

## 输出要求

1. 先问问题，等我确认
2. 确认后直接生成所有文件内容
3. 文件用代码块包裹，标注文件路径
4. 所有文档和注释使用中文
5. 不要生成业务代码本身，只生成规划文件和 prompt 指令
```

## 使用示例

假设你同事的需求文档是一个电商后台系统，他只需要这样发给 AI：

```
[粘贴上面的模板]

# 我的需求文档

我想做一个电商后台管理系统：
- 前端 React + Ant Design
- 后端 Spring Boot
- 商品管理、订单管理、用户管理
- 接入 AI 客服
- ...

# 我的技术偏好和环境

- 操作系统：Windows
- 包管理器：npm
- Java 版本：17
- 数据库：MySQL
- 部署：Docker
```

AI 就会按照模板，先问他一系列问题（数据库字段设计？AI 客服用什么模型？认证方式？等），
确认后生成跟我们这个项目一样完整的 .cursor/rules + docs + prompts 文件体系。

---

## 为什么这个方法有效

1. **需求澄清阶段**把模糊需求变成明确决策，消除歧义
2. **Cursor 规则文件**让 AI 编辑器自动理解项目上下文，减少重复解释
3. **AI 专用架构文档**解决了 AI 看不懂 ASCII 图表的问题
4. **PROJECT_STATUS.md** 解决了 Cursor 上下文窗口有限、跨会话失忆的问题
5. **原子化 prompt 文件**解决了 Cursor 无法一次执行大任务的问题
6. **每步验证 + git commit** 提供了安全回退机制

本质上，这套方法把一个"让 AI 做一个大项目"的不可能任务，
分解成了 40+ 个"让 AI 做一个小功能"的简单任务。
